# AI Report Analysis History Display Design

## Goal

Keep report-analysis conversations readable after reopening them from history. A user message generated by the **Phân tích bằng AI** action must display as a short business label instead of showing the embedded report JSON.

The raw message must remain unchanged in the database and API response so the backend can continue replaying the report data to the model for follow-up questions.

## Current Behavior

`buildAnalysisMessage` creates one user message containing both the analysis instruction and up to 12,000 characters of report JSON. During the live request, `useAiChat.deliver` shows a separate `displayText`, so the first user bubble is concise.

Only the full generated message is persisted. When `openSession` reloads the conversation, it copies `turn.content` directly into frontend state, causing the raw JSON to appear in both the AI dock and the full AI window.

## Scope

This change is frontend-only.

- Do not change the backend request or response contract.
- Do not add or migrate database columns.
- Do not modify the stored message.
- Do not change the message sent to the model.
- Apply the display behavior to both the AI dock and the full AI window through their shared `useAiChat` hook.

## Design

Add a small pure formatter for user-message display. It recognizes only the fixed report-analysis message shape produced by `buildAnalysisMessage`:

1. The message starts with `Đây là dữ liệu báo cáo "`.
2. A non-empty report name can be extracted from the generated prefix.
3. The message contains the generated `DỮ LIỆU:` JSON section marker.

When all conditions match, return:

```text
📊 Phân tích báo cáo "<report name>"
```

Otherwise return the original content unchanged. This prevents ordinary user messages or manually pasted JSON from being hidden accidentally.

`openSession` applies the formatter only to turns whose role is `USER`. Assistant narratives are never transformed.

The existing live path remains unchanged: `sendFresh` continues to use its supplied `displayText` immediately, while the formatter makes the restored-history path consistent with it.

## Data Flow

```text
AnalyzeButton
  -> buildAnalysisMessage(report name, raw report JSON)
  -> POST /api/ai/chat with the full message
  -> backend stores the full message

Open history
  -> GET /api/ai/conversations/{id}
  -> frontend receives the full stored content
  -> USER turn passes through the display formatter
  -> chat renders only the concise report label
```

Follow-up questions continue to work because the backend reconstructs model history from the unchanged database content, not from the frontend's formatted bubble text.

## Error and Compatibility Behavior

- Existing report-analysis conversations are formatted automatically when reopened because they use the same generated prefix and data marker.
- A malformed or partially matching message is displayed verbatim.
- A normal chat message is displayed verbatim.
- A manually pasted JSON message without the generated report-analysis envelope is displayed verbatim.
- The API still transfers the full stored JSON to the browser; the formatter changes presentation only.

## Verification

Add focused unit coverage for the pure formatter:

- Generated report-analysis content becomes the concise label.
- Normal user text remains unchanged.
- Manually pasted JSON remains unchanged.
- A partial/malformed generated envelope remains unchanged.

Verify that `openSession` applies the formatter only to `USER` turns and that both UI surfaces continue to consume the shared `useAiChat` state.

## Non-goals

- Reducing the conversation-history API payload.
- Removing or redacting JSON from the database.
- Changing how Azure OpenAI receives conversation history.
- Changing report analysis, tool routing, chart generation, or visualization validation.
